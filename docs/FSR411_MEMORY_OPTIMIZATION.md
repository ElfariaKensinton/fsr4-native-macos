# FSR 4.1: память и попытка ускорения — 2026-10-15

Цели **2–2,5 мс для Lite** и **3–3,5 мс для полного FSR 4.1** на M5
не достигнуты. Принятые изменения уменьшают scratch-буфер на 28,5% и
сокращают работу при сбросе истории. Устойчивое ускорение обычных кадров
по этим замерам не установлено. FSR 4.0.2 не изменён.

## Замер до и после

Apple M5, 10 GPU-ядер, 16 ГБ, macOS 27.0.1, питание от сети,
энергосбережение выключено. Записанная игровая последовательность:
864×560 → 1712×1112, восемь кадров, Auto Exposure и RCAS 0,401.

Шесть чередующихся серий по 30 последовательностей: **1440 измеренных
кадров на вариант**. Каждый запуск сначала прогревает одну последовательность.
В таблице медианы средних шести запусков; измеряется весь GPU command buffer.
Компиляция, чтение результата и диагностические счётчики в замер не входят.
История сбрасывается в начале каждой последовательности, первый кадр включён.

| Режим | До, мс | После, мс | Цель, мс |
| --- | ---: | ---: | ---: |
| FSR 4.1 Lite (`lossy`) | 3,092 | 3,042 | 2–2,5 |
| FSR 4.1 (`exact-fast`) | 4,395 | 4,359 | 3–3,5 |

Диапазоны средних запусков пересекаются: Lite 2,985–3,741 → 2,939–3,071;
полный 4.1 — 4,297–4,636 → 4,192–4,450 мс. Необычно медленный запуск
исходного Lite сохранён в данных. Температура и частоты GPU не фиксировались;
фоновые приложения продолжали работать.

Разделение кадров показывает, где изменился объём работы:

| Вид кадра | До, мс | После, мс |
| --- | ---: | ---: |
| Полный FSR 4.1, сброс истории | 5,149 | 4,632 |
| Полный FSR 4.1, без сброса | 4,288 | 4,307 |
| Lite, сброс истории | 5,001 | 4,609 |
| Lite, пересчёт сети без сброса | 4,267 | 4,282 |
| Lite, повторное использование сети | 1,733 | 1,720 |

В живой игре сбросы обычно реже, чем один на восемь кадров. Поэтому
уменьшение стоимости сброса нельзя переносить на каждый игровой кадр.

## Что это даёт в игре

Подтверждённого прироста среднего FPS нет. Даже если вся разница средних
0,037–0,050 мс сохранится в игре и ограничением будет GPU, условный расчёт
даёт около +0,03–0,05 FPS при 30 FPS, +0,13–0,18 при 60 FPS и +0,53–0,72
при 120 FPS. Это не замер FPS игры, а пересчёт времени: `1000 / (1000 / FPS − Δмс)`.
При ограничении CPU или частоты кадров такого прироста может не быть.
С учётом разброса замеров практически стоит рассчитывать на прежний средний FPS.

Экономия примерно 33 МБ относится к scratch-буферу одного FSR-контекста при
указанном tier. Влияние на производительность при нехватке общей памяти
отдельно не измерялось. Сокращение работы на кадре reset подтверждено,
но замера общей плавности игры или её 1% low нет.

## Принятые изменения

**POST-CNB использует освободившуюся память.** После pass12 последний CNB
читает только tensor A. Его выход теперь размещается после полной физической
области A, в уже не нужной части arena. Ни stride, ни веса, ни квантизация
не меняются. При повторном использовании нейросеть не запускается, и этот
кэш сохраняется; следующий полный проход обновляет его перед POST.

Для tier2160, выбранного при выходе 1712×1112, выделение уменьшается
с **116 409 856 до 83 232 256 байт**: экономия 33 177 600 байт.
Источник CNB занимает [0, 33 273 664), кэш начинается с 33 273 856;
области не пересекаются. Аналогичная проверка выполнена для 1080/4320.

Новый shader key `_ca1` и метаданные layout связывают адрес в POST с
адресом, который передаёт runtime. Старые кэши с `--no-compile` сохраняют
прежнее размещение после arena. Если новая сборка прервалась и содержит
неполный manifest, отсутствующие metallib или таблицы, runtime выбирает
готовый старый кэш. Проверка файлов выполняется при создании сессии;
загруженная сессия сохраняется до конца её использования. Полная сборка
с несовместимым layout по-прежнему отклоняется.
Reference сохраняет исходную компоновку.
Дампы scratch теперь описывают физическую компоновку: после POST байты
мёртвых промежуточных тензоров нельзя сравнивать с прежним полным дампом.

**При reset не очищаются три полностью перезаписываемые текстуры.** PRE
на таком кадре не читает историю или recurrent и заполняет reprojected;
POST заполняет history и recurrent. Инициализация exposure остаётся.
Если новые targets появляются без reset, их очистка сохраняется.
Это убирает ещё 38 074 880 байт записей на кадр сброса данной записи.

## Качество и проверки

**Все 96 RGBA16F-кадров совпали побайтно** с исходной рабочей версией:
четыре игровые записи × восемь кадров × `lossy`, `exact-fast`, `exact`.
Флаги reset/full/reuse совпали. Сохранены предшествующие исправления тонких
деталей Lite, веса, математические режимы, RCAS и частота пересчёта сети.

Отдельная проверка заполняет temporal textures NaN, Inf и произвольными
байтами перед reset, затем сравнивает весь выровненный viewport и следующие
кадры с чистыми текстурами. Проверены оба профиля, Classic Metal и Metal 4.
Тесты layout проверяют все три tier и отсутствие пересечения с источником CNB.

Прошли сборка и CPU-тесты, а также runtime (22 случая, 66 сравнений кадров),
reset, snapshot, cadence с несколькими кадрами в очереди, live integration,
SIMD, scalar, Lite, CLI и signed-chroma. Проверки shader-контрактов отдельно
подтверждают неизменность арифметики при переносе кэша и покрытие текстур
при reset.

Совместимость кэшей проверена отдельно: 21 проверка загрузчика и шесть
GPU-последовательностей по три кадра (reset/full, reuse, full). Они покрывают
неполный manifest, отсутствующие POST entry/metallib/таблицы, сохранение
загруженной сессии и отклонение неверного layout. Выходные кадры совпали
с legacy-кэшем побайтно.

Исправление выбора неполного кэша добавлено после основного замера и
затрагивает только CPU-загрузчик. GPU-код и его запуск совпадают с измеренным
кандидатом. После него заново собраны CLI и x86_64-библиотека для игры;
ещё 24 игровых кадра (`lossy`, `exact-fast`, `exact`) совпали с кандидатом
побайтно, включая расписание full/reuse и layout.

Для выпуска **v1.7** изменения перенесены на публичную v1.6 (`3c086d5`).
Существующие установщик и SIMD/Winograd сохранены. На этой сборке заново
прошли CPU-тесты, тесты установщика и все GPU-наборы, включая SIMD,
Auto Exposure, live integration и Metal 4. Ещё **96/96 игровых кадров**
совпали с измеренным кандидатом побайтно, включая cadence и layout.

Команды проверок, контрольные суммы исходников и все исходные числа находятся в
[JSON-отчёте](reports/fsr411-m5-memory-2026-10-15.json).

## Отклонённые эксперименты

Проверены другие размеры CNB, более крупные NF32, NF64 cooperative chains,
NF64 на двух SIMD-группах, отдельные POST для full/reuse, меньший shared cache
POST, распаковка CT2D-весов заранее, более узкие barriers и точные ограничения
размера группы при создании PSO. Устойчивого ускорения, оправдывающего их
включение, не получено; часть вариантов заметно медленнее.

Для NF64 tile8 MPP сохраняет ёмкость cooperative tensors как у tile16,
поэтому этот вариант исключён после layout probe. Счётчики по стадиям
использовались только для диагностики. Результаты промежуточных сравнений
сохранены в отчёте отдельно от заключительного A/B.

## Повторение

В текущем workspace сохранены исходная и выбранная версии, их кэши,
записи и план финального сравнения:

```sh
python3 tools/bench/benchmark_fsr411.py \
  build/target-ms-20261014/final-plan.json \
  build/target-ms-20261014/reproduced-benchmark --rounds 6 --bench 30
```

Каталог результата должен быть новым или пустым. Снимки исходников и
игровые записи находятся локально в `build/` и не входят в Git.
Для другого набора кадров передайте собственный plan JSON по примеру
в справке скрипта. GPU-тесты и бенчмарки запускаются последовательно.
